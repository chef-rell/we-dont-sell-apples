# WDSA v2 Specification — The Isometric Pivot

Status: **approved to build** (owner sign-off 2026-08-16). This document governs v2
scope, architecture, and phasing. `WDSA-game-spec.md` remains authoritative for every
v1 system this document does not supersede — in particular §6 (deterministic verdicts)
carries forward verbatim and inviolable. `v2-design-notes.md` is the vision capture
this spec was distilled from; where they differ, this spec wins.

Rollback point: tag `v1.5-playtest` (= `1c86399`, pushed to origin).

---

## V2.1 Locked owner decisions (2026-08-16)

1. **Art: procedural rects, extended to isometric.** No image assets. Production
   quality bar — *every generated visual must look finished* (see V2.4 for the
   enforcement rules). Wacom/Krita hand-drawn mockups serve as design references
   (palette, silhouette, proportion), never as shipped assets.
2. **Craft-track escape hatch: hired specialists.** No dead content — tracks the
   helper didn't take can be opened later by hiring specialists. The helper track
   stays meaningfully stronger on three axes: **earlier access, better quality,
   lower costs** (numbers in V2.9).
3. **Main stays always-shippable.** Railway deploys every phase. Every phase exits
   green (build + tests), playable, and tagged. `v1.5-playtest` is the rollback.
4. **Saves: fresh start.** v2 uses a new key `wdsa_save_v2` (switch happens at
   Phase 1). No migration in either direction. `wdsa_save_v1` is never read,
   written, or deleted by v2 code — pivoting back to the tag finds it intact.

Derived from the 2026-08-16 design review (owner may veto in PR review):

5. **The adventure strip is a playback, never a simulation** (V2.5). The renderer
   never decides outcomes — the §6 philosophy extended to combat.
6. **The existing ShopView remains the shop interior.** Clicking the shop in the iso
   town opens today's 2D interior (519 LOC of playtested polish). Iso-ifying the
   interior is explicitly out of scope for v2.0 (v1 spec §19 made the same call).
7. **Rarity and enchantments live in `baseValue`** (V2.9). The §6 reaction bands
   and verdict functions do not change.

## V2.2 Inviolable carryovers

All five hard rules in `CLAUDE.md` apply unchanged: §6 determinism, AI never
load-bearing, no secrets in public surfaces, the contract is sacred (additive +
flagged), module ownership (adapted in V2.13). New corollary of rule 1:

> **The renderer never decides outcomes.** Any v2 system that shows a fight, a
> death, a break, or a drop is performing a script whose facts were already final.

## V2.3 The triptych

Three synchronized panels, one story, **one game loop**:

- **Center — iso town** (primary surface): buildings, NPCs, queue, ambience.
- **Right — time column**: vertical dawn→night sky gradient, sun/moon marker
  (grown from the #52 day clock), phase labels, event markers, weather layer.
- **Bottom — adventure strip**: side-scrolling AdventureScript playback (V2.5).

Loop rule (the trap this exists to avoid): today each view owns a rAF loop and
calls `engine.tick` itself — three visible panels would tick the engine at 3×.
Phase 0 moves ticking to a single owner; every panel becomes a render-only
consumer of `engine.state`. Exact panel proportions and responsive behavior are
Phase 2 decisions, guided by the three prototype artifacts.

## V2.4 Iso rendering architecture

- **Projection module** (`src/rendering/iso.ts`): grid `(gx, gy, gz)` → screen,
  2:1 diamond tiles, chunky-pixel base `PX = 4` preserved. Draw order by painter's
  algorithm — sort key `(gx + gy)`, then `gz`. One shared module; no view does its
  own projection math.
- **Production-quality rules for procedural iso** (this is how rects look
  finished, codified so every building is consistent):
  1. Every solid is drawn as three faces from one base color via a shared shading
     util: top face light (+), left face mid (0), right face dark (−).
  2. Silhouettes get a 1-unit dark outline; no unshaded flat rect ever appears in
     the world view.
  3. All colors come from the shared palette in `constants.ts` — no ad-hoc hex in
     draw functions.
- **CharacterRenderer**: four diagonal facings (SE, SW, NE, NW — two drawn, two
  mirrored), 2-frame walk per facing plus an idle pose. `Position.facing` (already
  in the contract, currently ignored) becomes live. Equipped gear is drawn on the
  sprite — the sword you sold visible on the hip.
- Carry over unchanged: `ItemRenderer`, `ReactionRenderer`, `Particles`.

## V2.5 AdventureScript (the core new architecture)

Generated by `Combat` **at march time** with a seeded RNG; the seed is stored on
the script, so any run is reproducible (headless tests, balance harness, and a
future server replaying the same script byte-for-byte).

Shape (contract addition, exact fields finalized in the Phase 2 PR):

```
AdventureScript {
  id, day, seed, partyIds: string[], night: boolean,
  events: [{ t, type: "encounter" | "hit" | "gearBreak" | "retreat" | "death"
                 | "lootDrop" | "goldDrop" | "bossStart" | "victory" | "flee",
             actorId?, targetId?, itemId?, value? }],
  outcome: AdventureOutcome   // aggregate facts, final at generation
}
```

Rules:
- Who lives, what breaks, what drops, and how much gold enters town are **final
  the moment the script is generated**. The strip performs the events across the
  afternoon phase at presentation pace.
- If the tab suspends or a panel is hidden, game state advances from the script's
  outcome, never from animation progress.
- Night raids reuse this machinery — the mechanics already exist (threat ×1.5,
  gold ×1.6, guaranteed double loot); v2 adds the tavern decision beat and party
  presentation only.
- Gear drops render with shop name and paid price ("Iron Sword — 45g"); loot and
  gold arc toward the town panel on `goldDrop` events (the faucet, made visible).

## V2.6 Parties

v1 adventures are solo; v2 marches parties. This changes combat math, loot and
gold distribution, and — critically — the economy's failure modes.

- Noon: gathering at the gate, deterministic party formation (composition and
  membership are engine facts; AI writes banter only).
- Party power = aggregate member power + **diversity bonus** for distinct gear
  categories represented.
- Deaths are per-member; a full wipe kills everyone except the helper (V2.7).
- **Wipe stabilizer (mandatory, ships with parties):** the graveyard is
  functional, not flavor. Each death raises the newcomer arrival rate
  (avengers, fortune-seekers); replacements scale with body count so a wipe is a
  hard week, not an unrecoverable demand collapse. New NPCs visit the graveyard
  nervously — the flavor rides on the mechanic.
- **`scripts/balance-report.ts` gains party and wipe scenarios in the same PR
  that lands party combat.** Tuning must never go blind.

## V2.7 The Helper

- **Creation** at new game alongside the shopkeeper: appearance options (reuses
  the existing `appearance` system) + one trait — **Curious** (craft aptitude),
  **Brave** (adventure aptitude), **Charming** (shop aptitude). Aptitude = that
  track levels faster and unlocks stages earlier.
- **The shopkeeper is immortal; nobody in town knows.** Narrative hook only for
  v2.0 — no questline built now.
- **Days 1–10: general helper** (sweeping, chores — the tutorial). Day 10: the
  player picks ONE track. Hired specialists (V2.9) are the escape hatch for the
  other two — later, weaker, costlier.
- **Daily assignment is the core tension:** one job per day (shop duty,
  adventure, or craft task), assigned each morning.
- Tracks per the design notes: shop (register → pricing recs → solo shop-running,
  faster queue throughput), adventure (tag-along → fighter → scout → raid
  leader), craft (gardening → alchemy → blacksmithing, each unlocking a
  buildable structure).
- **Adventure-track helper always survives.** On a party wipe: solo return,
  dragging the loot sack through the strip — a scripted event type, not a
  renderer improvisation. Position in the marching order reflects level (back →
  front). Good performance earns reputation; near-death earns loyalty from
  guilty adventurers.

## V2.8 Property & buildings

- New contract collection **`GameState.buildings`**: fixed infrastructure
  (tavern, clinic, square, gate, graveyard, competitor stores) + player-plot
  structures (shop expansions, garden, alchemy lab, forge). Replaces the frozen
  `TOWN` literal and the two hand-coded click bboxes.
- Each building: id, kind, footprint, door, clickable flag; one shared hit-test
  util (`worldPointToBuilding`). Built in Phase 0 against the v1 top-down view so
  Phase 1 only swaps projection.
- Plot expansion direction is the player's choice and never impedes other plots
  (the multiplayer-safe constraint from the design notes).

## V2.9 Economy expansion

**Principle (from the design notes, adopted verbatim): the forge fills the floor,
the loot fills the showcase.**

- **Rarity**: common / uncommon (green) / rare (blue + sparkle) / legendary
  (purple-gold + persistent sparkle, gold name text). **Enchantments** (flame,
  skull, shield, heart icons) drop on loot only. Forge ceiling = uncommon; rare+
  is adventure-exclusive.
- **`baseValue` carries rarity and enchantment multipliers at item creation.**
  `Economy.ts` verdict functions and `REACTION_BANDS` are untouched — a legendary
  at 10× a forged item's price reads as *fair* because its baseValue says so.
- **Durability split**: forged gear = higher durability, no enchantments
  (bread-and-butter for daily runs); loot gear = lower durability, hits harder
  (brought out for bosses and night raids). Neither obsoletes the other.
- **Repairs** (the forge's service): price ≈ 35% of current item value; consumes
  monster materials; `timesRepaired` cap 2–3 (field already in the contract);
  each repair reduces `maxDurability` ~15%. Repair-vs-rebuy is a deterministic
  adventurer decision — a pure function in the `Economy.ts` style. These numbers
  exist to protect the durability → morning-shopping loop; tune them in
  `constants.ts` with the balance harness, never remove the cap.
- **Materials**: monster drops become crafting inputs; recipes unlock by deepest
  zone reached; day-30 forge gear needs day-30 monster parts. Adventure stays
  essential: faucet + materials + rare loot + recipe unlocks.
- **Hired specialists (the escape hatch, per locked decision 2):** any track's
  buildings/services can eventually be staffed by a hired townsperson, but the
  helper path is strictly better —
  - *earlier*: helper unlocks a stage at its skill milestone; the equivalent hire
    becomes available ~10–15 days later, gated on a reputation threshold;
  - *better*: hired output is one quality step lower and slower;
  - *cheaper*: hires cost an upfront fee plus an ongoing **percentage of sales**
    (payroll — a new gold sink that scales naturally with shop success).
  Hired staff come from a townsfolk pool, never from adventurers.
- **Competitor gold recycles.** Gold spent at NPC competitor stores returns to
  the adventurer economy as a small deterministic daily redistribution ("the town
  spends its money in town"). Bad player pricing is punished once (the lost
  sale), not twice (a drained money supply).
- **Weather** (time-column layer): affects adventure difficulty and availability,
  creating shop days vs adventure days. **Faucet guard:** no more than 2
  consecutive no-adventure days; on storm days the merchant injects gold. (The
  balance harness proved a stalled faucet stalls every sale.)
- **Reputation is persisted** on `GameState` (today it's recomputed at rollover
  and discarded). Feeds the shop-sign indicator and the market data window.

## V2.10 NPC competitor stores

Deliberately shallow — their jobs are (a) visible pricing pressure, (b) a
destination for angry customers, (c) the socket real players fill in multiplayer.
Static-ish price tables, limited rotating stock, no full inventory simulation.
Adventurer store choice is a deterministic comparison (pure function, §6 style);
AI voices the *opinion* about the choice, never the choice. If player prices are
bad, adventurers say so and walk — visibly.

## V2.11 Save policy

- Phase 0 adds `saveVersion: number` to the contract (`??= 1` on load).
- Phase 1 switches the storage key to **`wdsa_save_v2`** with `saveVersion: 2`.
- v1 saves: never read, never migrated, never deleted.
- The `??=`-defaults wall in `GameStatePersistence` continues for additive
  changes *within* v2; `saveVersion` exists so any future breaking shape change
  has a real gate instead of guesswork.

deployed via Railway, playable end-to-end, tagged.

## V2.13 Ownership & collaboration under v2

- Basmine (Dev B) works on an **availability basis**; Dev A carries the bulk,
  including temporary owner-sanctioned work inside Dev B domains — every such PR
  says so in its description.
- **Carved packages ready for Dev B whenever available** (isolated, contract-fed,
  no engine coupling):
  1. Adventure strip renderer — consumes `AdventureScript` only; the design notes
     already call it "own rendering system". The ideal first package.
  2. Iso building draw functions (V2.4 rules make these parallelizable).
  3. Weather layer (time column + town overlay).
  4. Audio pass — tavern/combat/weather ambience (Tone.js, optional,
     gesture-gated as always).
  5. CharacterRenderer facings/animation, if picked up before Dev A needs it.
- `App.tsx` and `types/index.ts` remain the coordinate-early shared files; the
  Phase 2 layout rewrite of `App.tsx` gets announced before it starts.

## V2.14 Multiplayer posture

Unchanged from v1 spec §19: future phases, backend proxy first. v2 adds exactly
one new prerequisite and satisfies it by design: adventure outcomes are seeded,
serializable scripts a server could generate and every client replay identically.
Keep honoring §19's standing constraints (serializable state, UUIDs, message
bus, renderer/logic separation, `makeDecision` as the swappable AI seam).
